## 1. Project overview

This is a single-user web application for a personal trainer. It allows the PT to:

- Manage multiple clients.
- Build weekly training schedules per client, defining training days, exercises, sets, reps, notes, and images.
- Maintain a shared exercise library with default sets/reps and images.
- Configure muscle groups and branding (PT name and logo).
- Save schedule templates and duplicate previous weeks.
- Export schedules as multi-page PDFs (one page per training day) in dark or light mode.

The application is self-hosted — it runs as a local web server on a Linux machine and is accessed through a browser on the same network.

## 2. Tech stack and dependencies

### Language
- **Python 3.10+** (tested on Python 3.12)

### Python packages (defined in `requirements.txt`)
| Package | Version | Purpose |
|---|---|---|
| `flask` | ≥ 3.0.0 | Web framework — serves the API and the frontend HTML |
| `weasyprint` | ≥ 61.0 | Server-side HTML-to-PDF conversion for schedule exports |

Flask includes `werkzeug` as a dependency, which is used for `secure_filename` when handling file uploads.

### System-level dependencies (Linux)
WeasyPrint requires several system libraries for rendering PDFs. These are installed automatically by `install.sh`:

- `libpango-1.0-0`, `libpangoft2-1.0-0`, `libpangocairo-1.0-0` — text rendering
- `libcairo2` — 2D graphics
- `libgdk-pixbuf2.0-0` — image loading
- `libffi-dev` — foreign function interface
- `shared-mime-info` — MIME type detection

On Ubuntu/Debian these are installed via `apt-get`. On Fedora/RHEL via `dnf`, on Arch via `pacman`.

### Database
- **SQLite 3** — built into Python's standard library, no separate installation needed. The database is a single file at `instance/rockson.db`.

### Frontend
- **Vanilla HTML, CSS, and JavaScript** — no build step, no frameworks, no npm. The entire frontend is one file: `templates/index.html`.
- Google Fonts (`Bebas Neue`, `DM Sans`) are loaded from a CDN at runtime. The app requires an internet connection for correct typography; it will still function without it but fonts will fall back to system defaults.

## 4. Installation

### Prerequisites
- A Linux machine (Ubuntu 20.04+ recommended, but any modern distro works)
- Python 3.10 or higher
- `pip` for Python 3
- `sudo` access (needed to install system packages and optionally configure systemd)
- Internet access (to download Python packages during setup)

### Steps

1. **Get the code onto the machine.** Either clone from GitHub or copy the files manually:
   ```bash
   git clone <repo-url>
   cd rockson
   ```

2. **Run the install script:**
   ```bash
   chmod +x install.sh
   ./install.sh
   ```

   The script does the following in order:
   - Checks that Python 3 and pip are available.
   - Installs WeasyPrint's system-level dependencies using the system package manager.
   - Creates a Python virtual environment at `venv/`.
   - Installs Flask and WeasyPrint into the venv.
   - Creates the `instance/` and `static/images/exercises/` directories.
   - Initialises the SQLite database by running `schema.sql`, which creates all tables and seeds default data (muscle groups, exercises, templates).
   - Writes `start.sh`.
   - Optionally installs a `systemd` service called `rockson-schedule` that auto-starts the app on boot.

3. **Open the app:**
   Navigate to `http://localhost:5002` in a browser. If accessing from another device on the same network, use the server's IP address instead of `localhost`.

### Firewall
If the server has `ufw` enabled and you want to access the app from other devices:
```bash
sudo ufw allow 5002
```

### Changing the port
Edit the last line of `app.py`:
```python
app.run(host='0.0.0.0', port=5002, debug=False)
```
Change `5002` to any available port. Then restart the app.

## 5. Running the app

### Start
```bash
./start.sh
```
This activates the venv and runs `python app.py`. The terminal will show request logs. Keep it open while using the app.

### Stop
Press `Ctrl+C` in the terminal where `start.sh` is running.

### If installed as a systemd service
```bash
sudo systemctl start   rockson-schedule
sudo systemctl stop    rockson-schedule
sudo systemctl restart rockson-schedule
sudo systemctl status  rockson-schedule
```

### After updating files
If you change `app.py` or `templates/index.html`, you need to restart the app for changes to take effect. There is no hot-reload in production mode.

### Backup
All data is in one file:
```bash
cp instance/rockson.db instance/rockson_backup_$(date +%Y%m%d).db
```

## 6. Database schema

The database is SQLite 3. The schema is defined in `schema.sql` and is applied automatically on first run via `init_db()` in `app.py`. All tables use `CREATE TABLE IF NOT EXISTS`, so running `init_db()` again on an existing database is safe — it will not overwrite data.

Foreign keys are enforced via `PRAGMA foreign_keys = ON`, set on every connection.

### Tables

#### `settings`
Key-value store for global configuration.
| Column | Type | Notes |
|---|---|---|
| `key` | TEXT (PK) | e.g. `pt_name`, `pt_logo`, `app_version` |
| `value` | TEXT | The setting value |

Default seed values: `pt_name = 'Rockson Performance'`, `pt_logo = ''`, `app_version = '1.0.0'`.

#### `muscle_groups`
Configurable list of muscle groups shown throughout the app.
| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER (PK) | Auto-increment |
| `name` | TEXT | Unique, e.g. `Chest`, `Quads` |
| `color` | TEXT | Hex colour code, used for pills and volume bars |
| `sort_order` | INTEGER | Display order in lists |
| `active` | INTEGER | 1 = active, 0 = hidden (not currently used in UI) |

11 muscle groups are seeded by default: Chest, Back, Shoulders, Biceps, Triceps, Quads, Hamstrings, Glutes, Lower Back, Core, Calves.

#### `exercises`
The shared exercise library. Exercises here are available to any client/schedule.
| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER (PK) | Auto-increment |
| `name` | TEXT | Exercise name |
| `muscle_group_id` | INTEGER (FK) | References `muscle_groups.id`, nullable |
| `default_sets` | INTEGER | Pre-filled when adding to a schedule |
| `default_reps` | TEXT | e.g. `"8-10"`, `"30s"` |
| `image_filename` | TEXT | Filename in `static/images/exercises/` |
| `is_default` | INTEGER | 1 = seeded by the app, 0 = added by user |
| `created_at` | TEXT | ISO datetime |

40 exercises are seeded by default across all muscle groups.

#### `clients`
| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER (PK) | Auto-increment |
| `name` | TEXT | Client full name |
| `notes` | TEXT | Optional free-text notes |
| `created_at` | TEXT | ISO datetime |

#### `templates`
Reusable schedule templates not tied to any specific client.
| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER (PK) | Auto-increment |
| `name` | TEXT | Template name |
| `description` | TEXT | Optional short description |
| `created_at` | TEXT | ISO datetime |

3 templates are seeded: Fullbody Hypertrophy, Push/Pull/Legs, Upper/Lower. Note: templates currently only store metadata (name/description) — they do not yet store exercise content. Loading a template from the UI creates a blank schedule; the template system is a foundation for future extension.

#### `schedules`
One schedule per client per week. A schedule is the top-level container.
| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER (PK) | Auto-increment |
| `client_id` | INTEGER (FK) | References `clients.id`, CASCADE delete |
| `template_id` | INTEGER (FK) | References `templates.id`, nullable |
| `week_number` | INTEGER | ISO week number 1–52 |
| `year` | INTEGER | e.g. 2025 |
| `date_start` | TEXT | ISO date string `YYYY-MM-DD` |
| `date_end` | TEXT | ISO date string `YYYY-MM-DD` |
| `status` | TEXT | `draft` or `final` |
| `notes` | TEXT | Optional notes |
| `created_at` | TEXT | ISO datetime |
| `updated_at` | TEXT | ISO datetime, updated on save |

Unique constraint on `(client_id, week_number, year)` — a client can only have one schedule per week per year.

#### `schedule_days`
Individual training days within a schedule.
| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER (PK) | Auto-increment |
| `schedule_id` | INTEGER (FK) | References `schedules.id`, CASCADE delete |
| `day_of_week` | INTEGER | 0 = Monday, 1 = Tuesday, … 6 = Sunday |
| `day_label` | TEXT | Custom label, e.g. `Day 1`, `Push A` |
| `sort_order` | INTEGER | Display order (usually matches `day_of_week`) |

#### `day_muscle_groups`
Many-to-many join between training days and muscle groups.
| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER (PK) | Auto-increment |
| `schedule_day_id` | INTEGER (FK) | References `schedule_days.id`, CASCADE delete |
| `muscle_group_id` | INTEGER (FK) | References `muscle_groups.id`, CASCADE delete |

#### `day_exercises`
Individual exercises within a training day. This is the most data-rich table.
| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER (PK) | Auto-increment |
| `schedule_day_id` | INTEGER (FK) | References `schedule_days.id`, CASCADE delete |
| `exercise_id` | INTEGER (FK) | References `exercises.id`, SET NULL on delete. Null if custom exercise. |
| `custom_name` | TEXT | Used when `exercise_id` is null (custom exercise not in library) |
| `muscle_group_id` | INTEGER (FK) | References `muscle_groups.id`, can override the library exercise's group |
| `set_code` | TEXT | Manual superset notation, e.g. `A1`, `B2` |
| `sets` | INTEGER | Number of sets |
| `reps` | TEXT | Rep range as free text, e.g. `8-10`, `30s`, `AMRAP` |
| `image_filename` | TEXT | Override image for this specific instance (in `static/images/exercises/`) |
| `notes` | TEXT | Instructions or cues for the client |
| `sort_order` | INTEGER (NOT NULL) | Display order within the day |
| `is_warmup` | INTEGER | 1 = warmup exercise, rendered separately in PDF |

**Important:** `sort_order` has a `NOT NULL` constraint. When updating a `day_exercise`, always include the current `sort_order` or read it from the database first. The `update_day_exercise` route in `app.py` handles this by reading the existing row before updating.

## 7. Backend: app.py

`app.py` is the entire backend. It is structured as follows:

### Initialisation
```python
BASE_DIR  = os.path.dirname(os.path.abspath(__file__))
DB_PATH   = os.path.join(BASE_DIR, 'instance', 'rockson.db')
IMG_DIR   = os.path.join(BASE_DIR, 'static', 'images', 'exercises')
ALLOWED   = {'png', 'jpg', 'jpeg', 'gif', 'webp'}
```
All paths are resolved relative to `app.py`, so the app can be run from any working directory.

`MAX_CONTENT_LENGTH = 8 * 1024 * 1024` limits uploads to 8 MB.

### Database connection management
`get_db()` opens a SQLite connection and attaches it to Flask's `g` object (per-request context). `close_db()` is registered as a teardown function so the connection is always closed after each request. `rows_to_list()` converts SQLite `Row` objects to plain Python dicts for JSON serialisation.

`init_db()` runs `schema.sql` against the database using `executescript()`. It is called once at startup via `if __name__ == '__main__': init_db()`.

### Route groups
The routes are grouped by resource in this order:
1. SPA serving (`/` and `/static/images/exercises/<filename>`)
2. Settings (`/api/settings`)
3. Muscle groups (`/api/muscle-groups`)
4. Exercise library (`/api/exercises`)
5. Clients (`/api/clients`)
6. Templates (`/api/templates`)
7. Schedules (`/api/schedules`, `/api/clients/<id>/schedules`)
8. Schedule days (`/api/schedules/<id>/days`, `/api/days/<id>`)
9. Day exercises (`/api/days/<id>/exercises`, `/api/exercises/day/<id>`)
10. PDF export (`/api/schedules/<id>/pdf`, `/api/schedules/<id>/pdf/preview`)

### PDF generation
Two functions handle PDF export:

**`_build_schedule_data(sid)`** — queries the database and assembles a complete Python dict representing the schedule, including all days, exercises, muscle groups, volume totals, and settings. This dict is passed to the renderer.

**`_render_pdf_html(data, mode)`** — takes the assembled dict and returns a complete HTML string. This HTML is then converted to PDF by WeasyPrint. The HTML is built entirely with inline styles (no external CSS) because WeasyPrint does not support all CSS features and inline styles are more reliable. The mode parameter is either `'dark'` or `'light'` and controls the colour palette used.

## 9. Frontend: index.html

The entire frontend is a single HTML file at `templates/index.html`. It is served by Flask as a static file — there is no server-side templating (no Jinja2). The page uses vanilla JavaScript to communicate with the backend API.

### Structure
The file is divided into three sections:

1. **`<style>` block** (~400 lines) — all CSS, using CSS custom properties (variables) for the colour palette and design tokens.
2. **HTML body** (~300 lines) — the static shell: topbar, sidebar, three screen containers, and all modal markup.
3. **`<script>` block** (~600 lines) — all application logic.

### Design system
The colour palette is defined as CSS variables in `:root`:
```css
--bg:      #0d0d0d   /* page background */
--surface: #141414   /* panels, topbar */
--card:    #1a1a1a   /* cards, rows */
--border:  #2a2a2a   /* all borders */
--gold:    #f9b233   /* primary accent — Rockson brand colour */
--text:    #f0f0f0   /* primary text */
--muted:   #666666   /* secondary text */
--danger:  #e05555   /* delete/error actions */
--success: #4caf50   /* final status */
```

Fonts: `Bebas Neue` (headings, large numbers) and `DM Sans` (body text). Both loaded from Google Fonts.

### JavaScript state object
All runtime data is held in a single `state` object:
```javascript
const state = {
  clients,         // array of all clients from API
  muscleGroups,    // array of all muscle groups
  exercises,       // array of all library exercises
  templates,       // array of all templates
  settings,        // key/value settings object
  activeClient,    // currently selected client object
  clientSchedules, // schedules for the active client
  activeSchedule,  // full schedule object currently open in the builder
  pdfMode,         // 'dark' or 'light'
};
```

### Screen routing
The app has three screens: `dashboard`, `builder`, and `settings`. `showScreen(name)` toggles which `.screen` div is visible and updates the active nav button.

### Data flow
1. On page load, `boot()` fetches all reference data in parallel (`clients`, `muscle-groups`, `exercises`, `templates`, `settings`) and stores it in `state`.
2. Selecting a client calls `selectClient(cid)`, which fetches that client's schedules and renders the dashboard.
3. Opening a schedule calls `openSchedule(sid)`, which fetches the full schedule (with nested days and exercises) via `GET /api/schedules/<id>` and stores it in `state.activeSchedule`.
4. The builder renders from `state.activeSchedule`. All inline edits (set code, sets, reps, notes) auto-save to the API after a 600ms debounce via `autoSaveExercise()`.
5. Weekly volume is recalculated client-side from `state.activeSchedule.days` whenever exercises change.

### Auto-save behaviour
When the PT edits a field in the exercise table (set code, sets, reps, or notes), a 600ms debounce timer fires `autoSaveExercise()`. This sends a `PUT /api/exercises/day/<id>` with only the four inline-editable fields. The backend preserves all other fields (especially `sort_order`) by reading the existing row first — this was a bug fix applied after initial deployment.

### Modals
All modals share the same `.modal-overlay` / `.modal` structure and are toggled with `openModal(id)` / `closeModal(id)`. The following modals exist:
- `modal-new-client` — create client form
- `modal-new-schedule` — create schedule (week number + year)
- `modal-duplicate` — duplicate a schedule to a new week
- `modal-template` — browse and load templates or previous client schedules
- `modal-add-exercise` — add exercise to a day (library tab or custom tab)
- `modal-add-mg` — add a new muscle group
- `modal-add-ex-lib` — add a new exercise to the library
- `modal-save-template` — save current schedule as a named template
- `pdf-preview-modal` — full-screen iframe preview of the PDF HTML

## 10. PDF export

PDF export is handled entirely server-side using WeasyPrint. The flow is:

1. The frontend calls `GET /api/schedules/<id>/pdf?mode=dark` (or `light`).
2. `export_pdf()` in `app.py` calls `_build_schedule_data(sid)` to assemble all data.
3. `_render_pdf_html(data, mode)` builds a complete HTML string with inline styles.
4. WeasyPrint converts the HTML to PDF bytes using `HTML(string=html_str, base_url=BASE_DIR).write_pdf()`.
5. The PDF is returned as a file download.

### PDF structure
Each training day is one A4 page (`page-break-after: always`). Each page contains:
- **Header** — PT name/logo text and client name + week number
- **Stats bar** — total workouts per week, total sets per week, current page/total pages, muscle groups for the day
- **Day heading** — day label (e.g. "Day 1"), day of week, exercise names as subtitle
- **Warmup rows** — if any exercises are marked `is_warmup = 1`, they appear in a highlighted row above the main table
- **Exercise table** — one row per exercise. If the exercise has an image, the row is tall (120px image on the right); if not, the row is compact.
- **Volume section** — bar chart showing total sets per muscle group for the whole week (same on every page)
- **Footer** — PT name, client name, week number, page number

### Inline styles only
WeasyPrint does not reliably support all CSS, especially `display: flex` in some contexts and CSS Grid. The PDF HTML uses only `display: table`, `display: block`, and explicit `width`/`padding` inline styles. Do not use CSS classes or a `<style>` block in the PDF HTML — WeasyPrint can struggle with these.

### Images in PDFs
Images are embedded using `file://` URIs pointing to the absolute path on disk:
```python
f'<img src="file://{img_path}" ...>'
```
This is why `base_url=BASE_DIR` is passed to WeasyPrint — it resolves relative paths correctly. Images must physically exist on disk; URLs to `/static/images/...` do not work in WeasyPrint (it does not make HTTP requests).

### Preview mode
`GET /api/schedules/<id>/pdf/preview` returns the raw HTML (not PDF) and is loaded in an `<iframe>` in the browser for a quick visual check before exporting. The iframe renders the HTML natively, which looks slightly different from the final PDF because browser rendering differs from WeasyPrint.

## 11. Image handling

### Upload locations
All images are stored in `static/images/exercises/`. There are two types:

**Library images** — attached to an exercise in the library. Filename: `exercise_<id>.<ext>`. Uploaded via `POST /api/exercises/<id>/image`. These appear on every schedule that uses that exercise, unless overridden.

**Day-exercise images** — attached to a specific exercise instance in a specific schedule day. Filename: `dex_<id>.<ext>`. Uploaded via `POST /api/exercises/day/<id>/image`. These override the library image for that one exercise on that one day.

### In the builder
In the exercise table, the photo cell shows either:
- A `+` placeholder (dashed border) if no image is set — clicking it opens a file picker and uploads via the day-exercise image endpoint.
- A thumbnail if an image is set. Currently clicking the thumbnail does nothing (replacement/removal UI is noted as future work).

### In the PDF
The PDF renderer checks `ex['image_filename']` (the day-exercise-specific image). If set and the file exists on disk, it renders the image at 120×120px. If not set, the row renders compactly without an image column. Library-level images are not currently used in PDF rendering — only day-exercise-specific images are.

### Allowed formats
`png`, `jpg`, `jpeg`, `gif`, `webp`. Maximum file size: 8 MB.

## 12. Known limitations and future work

The following features were discussed during development but not yet implemented. They are listed here so a future developer knows where to pick up.

**Image library browser** — when clicking the photo placeholder in the builder, the app should show a modal with two options: pick from existing uploaded images, or upload new. Currently it only supports uploading new.

**Image replace/remove** — once an image is set on a day exercise, there is no UI to replace or remove it. The backend supports it (just upload again or clear the `image_filename` field), but the frontend does not have the controls yet.

**Template exercise content** — templates currently only store a name and description. They do not store any exercise content. Loading a template from the modal creates an empty schedule. A future version should allow saving the full exercise structure of a schedule as a template that can be loaded as a starting point.

**PDF library images** — the PDF renderer only looks at `day_exercise.image_filename`. It should also fall back to `exercise.image_filename` from the library if no day-specific override exists.

**Client deletion confirmation** — deleting a client cascades to all their schedules. The UI should warn about this more prominently.

**Light mode for the app UI** — the app is dark mode only. The toggle in the topbar is a visual placeholder but does not function.

## 13. Making changes: guide for AI assistants

If you are an AI assistant helping to modify this application, read this section carefully.

### How to approach changes

**Always read the relevant section of this document first.** Before modifying a route, check the API reference. Before touching the frontend, understand the state object and data flow. Before changing the PDF, read the WeasyPrint constraints.

**The backend and frontend are tightly coupled.** If you add a field to a database table, you will need to update: the `schema.sql` definition, the relevant GET route (to return the new field), the relevant PUT/POST route (to accept it), and the frontend JavaScript that reads and writes that field.

**Database migrations.** SQLite does not support `ALTER TABLE ADD COLUMN` with NOT NULL constraints unless a default is provided. If you add a new column to an existing table, use:
```sql
ALTER TABLE table_name ADD COLUMN new_column TEXT DEFAULT '';
```
If the existing database has data and you run `init_db()` again, it will not re-create tables (because of `CREATE TABLE IF NOT EXISTS`) but it will not add new columns either. For a new column to appear in an existing database, run the `ALTER TABLE` statement directly against the database file using the `sqlite3` command-line tool, or add it to a migration script.

**Partial updates in the frontend.** The auto-save in the builder only sends the four fields that are inline-editable (set_code, sets, reps, notes). The `update_day_exercise` route compensates by reading the existing row first. If you add a new inline-editable field, add it to the payload in `autoSaveExercise()` in `index.html`.

**Frontend rendering pattern.** Most UI is rendered by JavaScript functions that build HTML strings and set `innerHTML`. To add a new column to the exercise table, you need to update: the `<thead>` in `renderDayPanel()`, the row in `renderExerciseRow()`, and the auto-save logic. Search for these function names in `index.html`.

**PDF changes.** The PDF HTML is built by string concatenation in `_render_pdf_html()` in `app.py`. Use only inline styles. Test with the preview endpoint (`/api/schedules/<id>/pdf/preview`) first, then check the actual PDF — they will look slightly different.

**Adding a new API route.** Follow the existing pattern: define the route with `@app.route(...)`, get the database with `db = get_db()`, fetch or modify data, call `db.commit()` for writes, and return `jsonify(...)`. Add the corresponding frontend call using the `api(method, path, body)` helper function in `index.html`.

**Toast notifications.** Call `toast('message')` for success and `toast('message', 'error')` for errors. These appear as a small notification at the bottom right of the screen.

**Modals.** To add a new modal, add its HTML markup (following the `.modal-overlay > .modal` structure) to the body of `index.html`, then call `openModal('modal-id')` and `closeModal('modal-id')` from JavaScript. Give each modal a unique `id`.
